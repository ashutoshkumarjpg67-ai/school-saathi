## v149 — bug 4 follow-up: the last false sync conflict (Marks 85 vs 85) + the Last-flush line

- **One false conflict left after v148 (bug 4):** the v148 live check showed \"Sync conflicts (6)\" — five genuine, but one false: Marks \"Yours Marks: 85\" vs \"Server Marks: 85\", identical values, only the ID formats differ. Root cause: the identical-content check compared the mapped payload field for field, including the foreign-key columns `exam_id`/`student_id`. The prune maps the recorded local row with the CURRENT id maps, while the recorded server row was matched with the maps at record time — for rows referencing seed exams/students the maps never resolve (seed rows are quarantined from upload, so their server rows carry no matching `local_id`), so the mapped payload carries null/stale UUIDs against the server row's real UUIDs and the comparison fails forever. The same trap bites attendance (matched by date+class+student).
- **Fix:** rows matched by NATURAL KEY carry their identity in the lookup, not in the compared fields — `sbSyncRowSameAsServer` now takes the table and skips the foreign-key identity columns for natural-key tables (`SB_SYNC_NATURAL_KEY_FKS`: `ss_marks` → `exam_id`, `student_id`; `ss_attendance` → `student_id`), so only content decides identical-ness. All 6 call sites pass the table (prune, school push branch, generic push branch, v127 guard). Deliberately NOT global: tables found by `local_id` keep the full comparison — a fee record moved to another student IS a real difference (`saveFeeRecord` lets the admin re-pick the student on edit), so `ss_fee_records`/receipts/homework still compare their foreign keys. The v148 test file never covered a marks identical-value case (only fee amounts) — which is why the bug survived.
- **Last-flush line agrees with the heading (bug 4):** the flush completion wrote this flush's newly recorded conflict count (`r.conflicts`) into the diagnostics, so Settings showed \"Last flush: pushed 0 · conflicts 0\" under a \"Sync conflicts (6)\" heading. It now stores the recorded total (`sbSyncRecordedConflictCount()`, returns `db.syncConflicts.length`), so the two always agree. The flush's `r.conflicts` return value is unchanged.

The display name comes from the LOCAL account record on the device (`loginAs` toasts `a.name`); `git diff 2ab6acda4..0270557 -- app.js` shows NO changes to the login/account-creation path — only the bug-3 city guards and bug-5 renamed-seed email.
